## Decision

A new explicit mobile file review may consume the unchanged bounded SiteX509AttendedUnlockV2 JSON only when the operator supplies an independently authenticated SHA-256 digest of the COMPLETE exact canonical challenge. This digest must come from the genuine host channel: strict known-host SSH and the fixed protected Monas-to-Thesaurophylax peer. The UI receives it through a separate manual field; imported bytes can never populate it. The programme owner authenticates the host through that channel and authorises the exact recipient through comparison. Face ID authorises the human action; it does not authenticate the host.

Before any Secure Enclave operation or scalar decryption, strictly parse all 32 digest bytes, reject duplicate/unknown/trailing/oversized JSON, use the existing complete V2 presentation parser, reconstruct its fully consumed challenge and compare SHA-256 to the independent digest. The challenge already binds schema/version, fixed role, Site, immutable custody generation/public key, encrypted-record digest, device/revocation, registration serial/expiry and fresh host recipient. The old host public point is not part of this canonical challenge. The parser checks its shape and that it differs from the fresh recipient; the existing producer authenticates that point through purpose-specific AEAD after signing and ECDH. A changed old point fails authenticated decryption before fresh rewrap or export. No old-point field is added to the wire.

The mobile adapter requires the existing protected Site Root ACK registration: a canonical Site UUID mapped to the existing site-UUID Trust Domain, positive current ACK generation and enrolled Site-root public-key hash matching the presentation device key ID. Decode targetIDB64URL as exactly 32 bytes and derive deviceKeyID as site-root- followed by lowercase hexadecimal of those bytes. ackPublicKeyB64URL names the separate ACK signing key and is never used to derive this X.509 device key ID. It reloads that record before production and denies replacement. It requires the existing Site-root Secure Enclave key and never creates a key. The existing producer checks the actual enrolled key ID and authenticated decrypted generation before rewrap. Missing protected record, wrong Site/device, stale expiry or key mismatch denies. History/display is not enrolment authority.

Retain one immutable validated presentation from comparison through review and proof. Display exact role, Site, immutable generation and fresh recipient. Capture those values once; disable input replacement during production, recheck expiry after fresh Face ID and before invoking the existing producer, and discard the prepared response on cancellation or changed inputs. Reuse existing proof, ciphertext and JSON response bytes. No new cryptographic scheme, signing key, COSE purpose, host signature or bearer credential is introduced.

The phone exports only the existing opaque submission file. It does not submit to HTTP or a caller-selected route, expose plaintext scalar/key, log proof/ciphertext contents, change trust, claim backend acceptance or report custody readiness. Existing claim history is preserved. The existing Thesaurophylax daemon still requires root then issuer in the same process before BOTH_READY; this phone interface does not establish issuer-only activation.

## Scope and actual caller

The first bounded source slice is the phone importer/review/exporter. Its real caller is an explicit mobile review flow receiving a fixed expected role, the unchanged genuine presentation and separately entered authenticated digest; after fresh Face ID it returns the existing opaque submission for the retained host stream. It enables no current installed ceremony by itself. Monas must separately implement a fixed-peer local adapter with a retained stream, fresh genuine challenge and exact protected bindings. The actual 30-second server submission timeout must be resolved in a coordinated accepted amendment before manual operation is qualified as usable.

The owner operation is concrete: obtain the complete challenge hash from the independently authenticated host session; enter that hash separately on Pistis; review the exact role/Site/generation/recipient; complete fresh Face ID; return the exported response to the same host attempt. No challenge, receipt, phone act or successful backend acceptance is fabricated by this decision. A consumed first-install transaction or one-use authority generation may not be reopened. Current custody eligibility and revocation remain backend prerequisites.

## Negative behaviour and atomicity

Reject wrong digest, recipient/role/generation/device/record substitution, imported digest fields, malformed digest, unknown/duplicate/trailing JSON, expired challenges, missing existing key/record and presentation/registration replacement. Importer, independent-digest, enrolled-binding and expiry rejection precedes proof production and decryption. The existing producer subsequently checks authenticated decryption and the recovered scalar public key before fresh rewrap and export. The phone holds no durable custody transition; the existing fixed server remains the sole one-use claim and acceptance writer. A lost response is not success, does not reset a claim and requires exact backend reconciliation.
