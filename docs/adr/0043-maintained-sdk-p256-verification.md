## Context

The current RustSec snapshot21d909e4 reports RUSTSEC-2026-0387 in the inherited
crypto-bigint0.5.5 graph. The maintained dependency family uses P2560.14 and
crypto-bigint0.7.8. Historical clean audits cannot clear the current graph.
The SDK's public PublicKey wraps a private verifier field; its public parser,
compressed SEC1 encoding and byte-signature verifier do not expose a raw Rust
curve type. This permits a compatible internal supplier correction. The human
Thesaurophylax1.0 implementation approval does not authorise additional public
breaks, live signing, phone installation, key replacement or data migration.

## Accepted decision

Use the reviewed maintained P2560.14 supplier through the existing workspace
curve declaration. Preserve the public opaque key and byte-facing API. Replace
only incompatible internal supplier calls with their maintained equivalents.
P2560.14 normalisation returns a signature directly: verification MUST compare
normalised and original values and continue rejecting high-S inputs. Signing
in test fixtures normalises to low-S. Do not accept a malleable twin by silently
normalising an incoming signature before verification.

Preserve exactly the ES256/SHA256 suite, 64-byte COSE r||s form, rejection of
DER/wrong-width/off-curve/infinity/hybrid/trailing encodings, compressed SEC1
canonicalisation and SHA256 domain `pistis:key-id:v1` followed by octet00.
No new algorithm, provider, transport, purpose, admission or fallback is added.
Existing retained originals, key IDs and private scalar/ciphertext formats do
not change. No secret is converted, copied or regenerated by this work.

Allocate pistis-crypto0.1.1, pistis-cose0.1.1 and pistis-protocol0.2.2 as already
reserved. The latter two retain their existing interoperability tests against
the maintained private curve implementation. Canonical0.1.1 source stays byte
identical. All four eventual immutable source pins move coherently; the Core
Linux same-source adapters must be checked for consistency without unrelated
phone features. Select the actual API carrier above for the existing workspace
Thesaurophylax edge; do not claim that its isolated carrier audit clears the
whole Pistis workspace or subsequent Core/Prox/Thes root graph.

## Qualification and failure behaviour

Keep and execute the RFC6979 known answer, low-S positive, high-S twin denial,
wrong-message/DER/wrong-width, SEC1 and stable key-ID tests. Preserve existing
COSE and protocol interoperability and negative fixtures. Add a fixed encoded
signature regression only if those existing cases leave a real gap; test
counts alone are not completion. Review API compatibility and actual resolved
supplier versions, generate a real lock through the maintained route, and run
component tests, warnings-denied lint, MSRV1.90, architecture/language and the
current strict paired security guard. Do not fabricate or hand-edit resolver
output, remove a test to break a dependency cycle, waive an advisory or present
a selected package result as whole-workspace acceptance.

The shared local capacity stop prohibits compilation or dependency fetching.
Source preparation and independent review can proceed; actual compilation,
lock generation and tests must use the existing maintained Alma lane after
its healthy priority work. Any unavailable fixture, changed public type,
failed wire fixture or remaining vulnerable supplier blocks qualification.

## Authority and scope

Pistis remains the cryptographic verifier/protocol owner. Core remains the
protected identity/session authority; Prox remains the Site writer; Thes owns
its existing private custody. There is no new transaction or mutable authority
store. This change does not weaken their currentness/deadline/secret boundaries.
Future continuity Core0.45/Prox0.71 and phone/private effects are separate.
Technical acceptance permits source implementation only. Final independent
implementation review and actual source/package/installed gates remain required.
